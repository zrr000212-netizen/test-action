# 阶段四：测试用例（Test Cases）

## 目标
设计 2-3 个真实场景的测试提示词，验证技能有效性。

## 测试用例格式（JSON）

```json
{
  "skill_name": "<skill-name>",
  "evals": [
    {
      "id": 1,
      "prompt": "用户可能说的话（真实、自然、有细节）",
      "expected_output": "期望技能的输出/行为",
      "files": []
    },
    {
      "id": 2,
      "prompt": "另一个真实场景的提示词",
      "expected_output": "期望输出描述",
      "files": []
    }
  ]
}
```

## 测试提示词设计原则

### 好提示词的特征

| 特征 | 示例 |
|------|------|
| **真实具体** | "老板刚发了我一个 xlsx（在下载文件夹，叫 'Q4销售最终版v2.xlsx'），她要我加一列显示利润率百分比。收入在 C 列，成本在 D 列。" |
| **有背景信息** | 包含文件路径、人物关系、时间压力等 |
| **多步骤** | 不能一步完成，需要多个工具协作 |
| **有明确目标** | 用户知道自己要什么（即使不知道怎么做） |

### 坏提示词的特征

| 特征 | 示例 | 问题 |
|------|------|------|
| 太简单 | "格式化这个数据" | LLM直接能处理，不触发技能 |
| 太抽象 | "帮我写代码" | 缺乏具体场景，无法验证技能效果 |
| 无上下文 | "读一下这个 PDF" | 任何LLM都能做，测试不出技能价值 |

## 设计步骤

1. **列出技能的3个核心场景**（从意图捕获阶段提取）
2. **为每个场景写一个具体提示词**（包含细节和背景）
3. **验证每个提示词确实需要技能才能完成**（简单查询不需要技能）
4. **提交胖教练审阅**（确认覆盖了关键场景）

## 保存位置

```json
// 保存到技能目录下
~/.agents-shared/skills/<skill-name>/evals/evals.json
```

## 多Agent测试

如果技能涉及多 Agent 协同：
- 明确哪个 Agent 使用技能执行任务
- 另一个 Agent 作为评审者给出反馈
- 通过共享目录交换测试结果

## 注意事项

- 测试用例要随技能迭代更新
- 数量以 2-3 个为宜（太多维护成本高）
- 优先选择**边界情况**而非显而易见的情况
